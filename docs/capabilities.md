# Capability map

This map connects reviewer-visible workflows to their behavior and verification. The [design](design.md) explains the concurrency and durability model; the [operations runbook](operations.md) covers recovery. Provider simulators and fault injection belong to isolated tests. The working console shows persisted account, automation, conversation and delivery data, including honest empty and unconfigured states.

The [integration guide](integration.md) is the canonical machine-client guide, with the [OpenAPI contract](../src/api/openapi.json). A running API serves `/docs`. The [public documentation site](https://psy-labs-admin.github.io/blotato-comment-automation/) hosts documentation only; it has no customer workspace, operator login or webhook receiver.

## User and operator workflows

| Workflow | Implemented behavior | Details and evidence |
|---|---|---|
| Open a workspace | Quickstart provisions a local installation; a one-use sign-in ticket opens a tenant-bound browser session. An empty workspace does not invent accounts, conversations or activity. | [Access and key administration](operations.md#api-access); [session tests](../tests/integration/session.test.ts), [operator tests](../tests/integration/operator.test.ts) |
| Connect an account | Native Instagram Login checks single-use state, initiating session, grants, account identity and webhook subscription before saving encrypted credentials. Reconnect and refresh use credential-generation fencing. Disconnect removes the local token and stops new sends; it does not revoke the Meta grant. | [Connection lifecycle](instagram.md); [OAuth tests](../tests/integration/instagram-oauth.test.ts), [native send-generation tests](../tests/integration/instagram-send-generation.test.ts) |
| Draft, edit and publish | Save partial drafts, select a connected account and publish validated content. Revision checks prevent lost edits. Publishing creates an immutable version; running conversations retain their pinned version. | [Definitions and versions](design.md#3-how-general-is-the-engine-and-why); [operator tests](../tests/integration/operator.test.ts), [public API tests](../tests/integration/public-api.test.ts) |
| Disable a rule or pause an account | Disabling a rule stops new runs while existing runs continue. Account pause suppresses new runs and defers sends at the policy gate; resume permits eligible waiting work. A long deferral can expire and platform windows still apply. | [Controls](operations.md#controls); [policy gate](../src/policy/gate.ts), [cancel/stop tests](../tests/failure-scenarios/cancel-and-stop.test.ts) |
| Follow a comment to a link | Whole-word keyword matching chooses one rule by priority, reserves one conversation, sends a public reply/private question, captures one valid email and sends the link by DM. Deduplication, cooldown and one active run constrain repeat triggers. | [Product contract](design.md#2-product-contract); [native journey](../tests/integration/native-journey.test.ts), [duplicate tests](../tests/failure-scenarios/duplicates.test.ts) |
| Handle early or invalid replies | A reply received after question reservation remains eligible while its send is in flight. Fixed boundaries exclude older messages; the absolute deadline survives retries. Invalid answers receive bounded clarification; an admissible valid reply wins before expiration. | [Waits and races](design.md#8-waiting-for-input-boundary-deadline-and-races); [race tests](../tests/failure-scenarios/races.test.ts), [wait tests](../tests/integration/waits.test.ts) |
| Respect consent and handoff | STOP/opt-out durably blocks further automated sends and cancels the active run. Human takeover also cancels the active run and blocks future triggers; releasing takeover permits future triggers without reviving that run. Email format validation does not verify ownership or establish marketing consent. | [Controls](operations.md#controls), [product rules](design.md#2-product-contract); [cancel/stop tests](../tests/failure-scenarios/cancel-and-stop.test.ts) |
| Cancel a run | The authoritative control is committed with a workflow wake-up. Each send checks it. A request cannot recall a network call already in flight; unresolved sends continue holding the conversation. | [Change management](design.md#13-change-management); [cancel/stop tests](../tests/failure-scenarios/cancel-and-stop.test.ts) |
| Investigate an uncertain send | An ambiguous external result becomes `unknown`, holds the conversation and opens an incident. No blind resend occurs. An operator verifies Instagram evidence before resolving accepted or authorizing one deliberate new attempt; incorrect authorization can duplicate a delivered message. | [Ledger and recovery](design.md#7-external-sends-the-ledger-protocol), [incident playbook](operations.md#send_outcome_unknown-instagram-may-or-may-not-have-received-a-message); [crash tests](../tests/failure-scenarios/crash-and-unknown.test.ts) |
| Inspect a conversation | Run/conversation timelines explain recorded routing, waits, send acceptance, controls and end states. The funnel counts run cohorts. Instagram acceptance does not imply delivery, reading or clicking. | [Observability](design.md#12-observability); [timeline implementation](../src/timeline.ts), [API tests](../tests/integration/api.test.ts) |
| Capture leads and sync CRM | A valid answer creates one provenance-linked, format-valid/unverified lead and a durable CRM job. CRM failure does not block the DM link. Repeated requests carry the same idempotency key, which the CRM must honor. | [CRM recovery](operations.md#crm_delivery_failing); [integration tests](../tests/integration/integrations.test.ts), [CRM failure tests](../tests/failure-scenarios/crm-and-alerts.test.ts) |
| Show post context | Native Graph or gateway metadata is fetched asynchronously and cached. Missing, denied and unavailable metadata remain explicit; hydration failure does not block the conversation. | [Metadata and retention](operations.md#metadata-and-data-retention); [metadata tests](../tests/integration/metadata.test.ts) |
| Retry stopped background work | Operations offers a reasoned, revision-checked retry only for eligible stopped CRM/metadata jobs with a healthy consumer. Ownership, target checks, generation increment and audit commit together. Social sends, workflow commands and incident notifications have different recovery paths. | [Recovery](monitoring.md#recovery); [operations tests](../tests/integration/operations.test.ts), [dead-letter race tests](../tests/integration/dead-letter-races.test.ts) |
| Receive operational notifications | A deployment-managed Telegram chat or webhook receives grouped incident notifications. Receipts, shared flood waits and ordering are persisted. Unconfigured delivery stays pending. Telegram has no send idempotency key; an uncertain transport outcome can duplicate a retry. | [Telegram behavior and explicit checks](telegram.md); [alert delivery tests](../tests/integration/alert-delivery.test.ts) |
| Integrate another backend | Named tenant-bound machine keys allow read access or read/write access to `/api/v1`; secrets are returned once and stored only as SHA-256 digests. Revocation is checked against PostgreSQL on every request. Operator, cookie and metrics authentication remain separate. | [Integration guide](integration.md), [OpenAPI](../src/api/openapi.json); [key tests](../tests/integration/integration-keys.test.ts), [contract tests](../tests/integration/openapi-contract.test.ts) |

## Deployment, privacy and verification

| Concern | Implemented behavior and boundary | Reference |
|---|---|---|
| Native versus gateway ingress | Native callbacks verify raw-body Meta signatures and durably ingest supported events before acknowledging; the relay sweeps them for routing. Gateway mode verifies a separate timestamped HMAC and attempts inline routing before returning 202. Both paths deduplicate persisted events and recover pending routing. | [Execution model](design.md#6-execution-model); [native webhook tests](../tests/integration/instagram-webhook.test.ts), [routing tests](../tests/integration/routing.test.ts) |
| Tested integration modes | Contract tests exercise native Instagram Login/Graph/OAuth, signed native ingestion and an isolated native journey; gateway tests exercise normalized events and authenticated transport. These checks use controlled providers, not a live approved Meta app. Meta Unified Login / Facebook Login for Business configuration IDs are not implemented. | [Instagram setup and live verification](instagram.md#connect-and-verify); [testing guide](testing.md) |
| Stable live deployment | Real native operation requires an eligible authorized professional account, applicable app approval, stable public HTTPS callback/webhook routes, explicit capability limits, secret/encryption-key management, persistent PostgreSQL/Temporal and running worker/relay roles. The supplied TLS Compose example expects those external services; local editing or a webhook challenge alone does not prove live delivery. | [Prerequisites](instagram.md#before-enabling-a-workspace), [deployment example](instagram.md#deploy-a-public-callback-host), [runbook](operations.md#deploying) |
| Operational monitoring | Process, database and pipeline readiness are distinct. Fresh observed role health, configured-destination queues, routing lag and unknown-send age feed the shipped Prometheus rules. An independent monitor can notify on application failure; a monitor on the same host cannot detect that host losing power. | [Monitoring](monitoring.md), [actual thresholds](operations.md#signals-to-watch) |
| Privacy and retention | Native tokens are encrypted and tenant-bound; browser sessions are HttpOnly. Logs, alerts and traces exclude message bodies and emails. Inbox redaction is opt-in and skips active/held conversations while preserving deduplication and audit facts. Leads, metadata and backups still require restricted access, encryption and operator retention/deletion policies. | [Retention](operations.md#metadata-and-data-retention); [retention tests](../tests/integration/retention.test.ts), [access tests](../tests/integration/access.test.ts) |
| Diagnostic tracing | Opt-in OTLP spans use allowlisted fields; a collector failure does not block webhook acceptance. Trace context stays within a process; durable timelines and metrics provide cross-process facts. | [Tracing](observability.md#opentelemetry-tracing); [tracing tests](../tests/integration/tracing.test.ts) |
| Restart and worker upgrades | PostgreSQL stores facts, Temporal owns durable orchestration. Restart, crash, replay and continue-as-new checks preserve the ledger and fixed deadlines. Optional pinned worker deployments require a compatible Temporal server and an explicit rollout; old workers must drain. | [Worker upgrades](worker-upgrades.md); [restart tests](../tests/failure-scenarios/restart.test.ts), [replay tests](../tests/integration/replay.test.ts), [rollover tests](../tests/integration/rollover.test.ts) |
| Acceptance and capacity | Verification uses throwaway databases, real Temporal/HTTP and controlled providers; it includes browser flows, process/container checks and monitoring configuration. The load report describes a bounded synthetic local run, not a production capacity promise or a live Instagram certification. | [Testing](testing.md), [load methodology](observability.md#reproducible-load-check) |

There is no visual graph editor, arbitrary user-code execution, multi-platform adapter implementation, email ownership verification or automatic Meta data-deletion/deauthorization callback. Those boundaries do not prevent the implemented comment → email reply → DM-link workflow; they matter when extending it into a hosted production product.
